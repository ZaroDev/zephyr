# Build System

Zephyr is built with [Premake5](https://premake.github.io/), not CMake. There is no
`CMakeLists.txt` anywhere in the tree; project/solution generation is driven entirely by Lua
scripts and a vendored `premake5` executable checked into the repo.

## Layout

```
Build.lua                     workspace root (premake5 entry point)
Dependencies.lua               include/lib path tables, included by Build.lua
Engine/Build-Engine.lua        Engine static-lib project
Editor/Build-Editor.lua        Editor application project
Engine/Vendor/*/premake5.lua   one premake script per vendored dependency that builds from source
Scripts/Setup-Windows.bat      runs vendored premake5.exe against Build.lua -> vs2022
Scripts/Setup-Linux.sh         runs vendored premake5 against Build.lua -> gmake2 (clang)
Vendor/Binaries/Premake/       prebuilt premake5 binaries for Windows/Linux/macOS
```

`Build.lua` is the single workspace file (`workspace "Zephyr"`). Nothing else declares a
`workspace` block; every other `premake5.lua` in the tree only declares `project` blocks and is
pulled in via `include(...)` from `Build.lua`.

## Generating and building

There's no CMake-style `configure` step. Project files are generated by running the vendored
premake5 binary against `Build.lua`:

- Windows: `Scripts\Setup-Windows.bat`, which effectively runs
  `Vendor\Binaries\Premake\Windows\premake5.exe --file=Build.lua vs2022` from the repo root and
  pauses afterward. This produces `Zephyr.sln` plus a `.vcxproj` per project at the repo root
  (a `Zephyr.sln` already exists in the tree from a previous generation).
- Linux: `Scripts/Setup-Linux.sh`, which runs
  `Vendor/Binaries/Premake/Linux/premake5 --cc=clang --file=Build.lua gmake2`, producing
  Makefiles instead of a Visual Studio solution.
- A macOS `premake5` binary is also vendored at `Vendor/Binaries/Premake/macOS/premake5`, but
  there is no corresponding `Scripts/Setup-macOS.sh` — macOS generation would have to be invoked
  by hand (e.g. `premake5 --file=Build.lua xcode4`), and the GLFW vendor script does contain a
  `system:macosx` filter, so macOS is at least partially plumbed for, just not wired into a setup
  script.

After generation, building is a normal Visual Studio (`msbuild Zephyr.sln` or opening the
solution) or `make` invocation — Premake itself does not compile anything.

## Workspace configuration

Declared once at the top of `Build.lua`:

- `architecture "x64"` — no 32-bit target.
- `configurations { "Debug", "Release", "Dist" }`.
- `startproject "Editor"`.
- On `system:windows`, workspace-wide `buildoptions { "/EHsc", "/Zc:preprocessor",
  "/Zc:__cplusplus" }` and two deprecation-warning-silencing `defines` are applied to every
  project.
- `outputdir` is the shared string `"%{cfg.system}-%{cfg.architecture}/%{cfg.buildcfg}"`, used by
  every project/vendor script to build output paths such as
  `Binaries/windows-x64/Debug/Engine`.

### What differs per configuration

The three configs are handled per-project via `filter "configurations:X"` blocks; the pattern is
consistent across Engine, Editor, and every vendor project, though the exact defines differ:

| Config | Engine defines | Editor defines | Editor `kind` | runtime/optimize/symbols |
|---|---|---|---|---|
| Debug | `DEBUG`, `ENABLE_ASSERTS` | `DEBUG`, `WINDOWS` | `ConsoleApp` | Debug runtime, symbols on, no optimization |
| Release | `RELEASE`, `ENABLE_ASSERTS` | `RELEASE`, `WINDOWS` | `ConsoleApp` | Release runtime, optimize on, symbols **on** |
| Dist | `DIST` | `DIST`, `WINDOWS` | `WindowedApp` | Release runtime, optimize on, symbols off |

Notable details:
- `ENABLE_ASSERTS` is defined in both Debug and Release, not just Debug — assertions
  (`Core/Assert.h`) are compiled out only in Dist.
- Only Dist switches Editor's `kind` to `WindowedApp` (no console window); Debug and Release both
  build the Editor as a `ConsoleApp` so log output is visible.
- Most vendor projects (GLFW, ImGui, NVRHI\*) use `optimize "speed"` for Release/Dist while
  ImGui uses plain `optimize "on"` — a minor inconsistency but not a functional bug.
- GLFW's script additionally has a `configurations:Debug-AS` filter (an AddressSanitizer debug
  config) that isn't one of the three configurations declared in `Build.lua`'s workspace, so it
  is currently dead/unreachable — likely left over from another project this vendor script was
  copied from.

## Project/group structure

`Build.lua` organizes projects into three Visual-Studio solution folders ("groups"), included in
this order:

```
Build.lua
 ├─ include "Dependencies.lua"          (no project; just sets IncludeDir/LibraryDir/Library tables)
 │
 ├─ group "Engine"
 │   └─ Engine/Build-Engine.lua          project "Engine"        (StaticLib)
 │
 ├─ group "Engine/Dependencies"
 │   ├─ Engine/Vendor/GLFW               project "GLFW"          (StaticLib)
 │   ├─ Engine/Vendor/glad               project "glad"          (StaticLib)
 │   └─ Engine/Vendor/ImGui              project "ImGui"         (StaticLib)
 │
 ├─ group "Engine/Dependencies/NVRHI"
 │   └─ Engine/Vendor/NVRHI *            project "NVRHI-Vulkan"  (StaticLib)
 │                                       project "NVRHI-D3D11"   (StaticLib)
 │                                       project "NVRHI-D3D12"   (StaticLib)
 │                                       project "NVRHI"         (StaticLib, links the three above)
 │
 └─ group "Editor"
     └─ Editor/Build-Editor.lua          project "Editor"        (ConsoleApp/WindowedApp, links "Engine")
```

Build order is whatever premake/msbuild resolves from `links {}` dependencies, not from the
`include` order above — but the `include` order does determine solution-folder grouping and is a
reasonable mental model: engine-internal dependencies build before Engine, Engine builds before
Editor, and the four NVRHI static libs (Vulkan/D3D11/D3D12 backends + the umbrella `NVRHI`
project that links all three) build before anything that links plain `"nvrhi"`.

`assimp` and `meshoptimizer` are **not** premake subprojects — they are consumed as prebuilt
`.lib` files via `Dependencies.lua`'s `Library` table (see `docs/vendor.md`), so they don't
appear in this project graph at all; they're linked directly into `Engine`.

## Known inconsistencies

- **`Engine/Vendor/NVRHI` vs `Engine/Vendor/nvrhi` casing (confirmed real).** `Build.lua` line 27
  does `include "Engine/Vendor/NVRHI"` (capital `NVRHI`), but the directory that actually exists
  on disk — and the one referenced everywhere else (`Dependencies.lua`'s
  `IncludeDir["nvrhi"]`, `.gitmodules`, `git submodule status`) — is `Engine/Vendor/nvrhi`
  (lowercase). This currently works only because Windows' filesystem (and this repo's git config,
  `core.ignorecase = true`) is case-insensitive. It would fail to resolve on a case-sensitive
  filesystem (Linux/macOS, or a case-sensitive Windows volume), which is directly relevant since
  `Scripts/Setup-Linux.sh` exists and targets Linux. This should be fixed to `Engine/Vendor/nvrhi`
  for cross-platform correctness.
- **`Engine/Vendor/ImGui` shows as untracked in `git status` despite being a working, correctly
  pinned submodule (confirmed real, root cause identified).** `git submodule status` reports it
  cleanly at commit `d5b98cb19...` and `git ls-files --stage` shows a normal `160000` gitlink
  entry for it in the index — so it isn't simply "not committed." The cause is a stale submodule
  *name* left over from before the vendor tree was reorganized: `.gitmodules` still declares the
  section as `[submodule "Editor/Vendor/ImGui"]` (with `path = Engine/Vendor/ImGui` inside it),
  i.e. the submodule was originally checked out under `Editor/Vendor/` and later moved to
  `Engine/Vendor/` without renaming the submodule section to match, and `.git/modules/` still has
  the module's git data stored under `Editor/Vendor/ImGui` internally. GLFW and nvrhi don't have
  this split (their `.gitmodules` section names match their current paths), which is why only
  ImGui shows this symptom. It's cosmetic (the submodule itself resolves and builds fine) but
  worth cleaning up (`git config --file .gitmodules --rename-section
  submodule.Editor/Vendor/ImGui submodule.Engine/Vendor/ImGui`, and likewise moving the
  `.git/modules` entry) to stop it showing as a dirty/untracked path.
- **enkiTS is vendored but not wired into the build at all.** `Engine/Vendor/enkiTS/` exists on
  disk (untracked, i.e. freshly dropped in and not yet committed) but is referenced nowhere in
  `Build.lua`, `Dependencies.lua`, or `Engine/Build-Engine.lua` — see `docs/vendor.md` for
  details.
- **`README.md` at the repo root is empty** (0 bytes) — there is currently no top-level project
  description; anyone landing on the repo has to read `Build.lua`/`docs/` to understand what it
  is.
- Root `.gitignore` excludes `*.vcxproj`, `*.sln`, and `Binaries/` from version control (in
  addition to the usual `.vs/`), consistent with the generate-on-demand workflow above: the
  checked-in `Zephyr.sln` and any `.vcxproj` files in the working tree are therefore local,
  regenerable artifacts, not something to hand-edit or expect to match what's on a clean clone
  before running the setup script.
