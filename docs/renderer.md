# Renderer

`Engine/src/Zephyr/Renderer/` is where Zephyr's rendering code lives: the camera math, the render-pass interface, shader compilation/loading, and — most importantly for understanding the current state of the engine-overhaul branch — **two independent device/swapchain abstractions that coexist mid-refactor**. One (`DeviceManager` and its `D3D11`/`Vulkan` platform subclasses, plus `IRenderPass`/`ImGuiRenderPass`) is a fully-featured stack ported from NVIDIA's donut/nvrhi example framework; the other (the new `Renderer` `IModule` class, which delegates to `Zephyr::RHI::Device` — see `docs/rhi.md`) is the small, currently-skeletal replacement that is actually wired into the running application. This module exists to own everything "camera + GPU device + swapchain + shaders + immediate-mode UI" that sits between the engine's `IModule`/`Application` layer and nvrhi.

## Key Files

| File | Purpose |
|---|---|
| `Renderer/Camera.h` / `.cpp` | `Camera` class: view/projection matrices, FOV, near/far planes, mouse-driven orbit/fly controls (currently disabled — see Design Notes). |
| `Renderer/DeviceManager.h` / `.cpp` | Legacy/parallel abstract device+swapchain+render-loop manager (donut-derived). Owns the GLFW window, drives the animate/render/present loop, and dispatches to a list of `IRenderPass`es. Not instantiated anywhere in the current build. |
| `Renderer/Platform/D3D11/D3D11DeviceManager.h` / `.cpp` | Concrete `DeviceManager` for D3D11. Fully implemented (real device/swapchain/adapter-enumeration code), but orphaned along with the base class. |
| `Renderer/Platform/Vulkan/VulkanDeviceManager.h` / `.cpp` | Concrete `DeviceManager` for Vulkan. The largest file in the module (~45 KB); fully implemented Vulkan instance/device/swapchain setup (extensions, queue families, debug callback, etc.), also orphaned. |
| `Renderer/IRenderPass.h` / `.cpp` | Interface for pluggable render passes registered with a `DeviceManager` (`Render`, `Animate`, resize/DPI/input callbacks). `.cpp` is empty (all defaults live in the header). Only meaningful in combination with `DeviceManager`, which is currently unused. |
| `Renderer/RenderPasses/ImGuiRenderPass.h` / `.cpp` | `IRenderPass` implementation that renders Dear ImGui via a hand-written nvrhi backend (`ImGui_NVRHI`, "From donut"). Depends on `DeviceManager`/`IRenderPass`, so it inherits their orphaned status — never constructed anywhere in the codebase. |
| `Renderer/Renderer.h` / `.cpp` | **New.** `Renderer` : `IModule` — the class actually registered with `Application`'s `ModuleManager`. Currently just creates an `RHI::Device` and does nothing else. |
| `Renderer/ShaderFactory.h` / `.cpp` | Compiles `.slang` shader source to platform bytecode (DXBC/DXIL/SPIR-V) via the Slang compiler API, caches compiled bytecode to `.bin` files, and wraps `nvrhi::IDevice::createShader`/`createShaderLibrary`. API-agnostic; not tied to either device stack. |

## Key Types & APIs

- **`Zephyr::Camera`** (`Camera.h`/`.cpp`) — holds `Mat4` projection/view/inverse matrices, FOV/near/far, position, forward direction, and an orbit target. `OnUpdate(ts)` is meant to poll `Zephyr::Input` for fly/orbit controls and recompute the view matrix; `OnResize(w, h)` recomputes projection. Despite the class doc-comment ("Definition of a 3D orthographic camera") and the `CameraParameters` (`Top/Bottom/Left/Right`) it computes in `OnResize`, `RecalculateProjection()` actually builds a **perspective** projection via `glm::perspectiveFov` and never reads `m_Parameters` — the orthographic bounds are computed but unused. Treat the "orthographic" doc-comment as stale.

- **`Zephyr::DeviceManager`** (`DeviceManager.h`/`.cpp`) — abstract class combining what `RHI::Device` + `RHI::Surface` + a render loop would eventually cover: `CreateWindowDeviceAndSwapChain()` / `CreateHeadlessDevice()`, GLFW window creation and hint setup based on `DeviceCreationParameters`, `Update()` (the actual `while (!glfwWindowShouldClose)` loop calling `AnimateRenderPresent()`), `AddRenderPassToFront/Back`/`RemoveRenderPass`, DPI-scale tracking, and pure-virtual device-specific hooks (`CreateInstanceInternal`, `CreateDevice`, `CreateSwapChain`, `BeginFrame`, `Present`, etc.) that subclasses implement. `DeviceManager::Create(GraphicsAPI)` factory dispatches to `CreateD3D11()`/`CreateD3D12()`/`CreateVK()`; `CreateD3D12()` simply `return nullptr` (D3D12 was never implemented here either).

- **`Zephyr::D3D11DeviceManager`** / **`Zephyr::VulkanDeviceManager`** (`Platform/D3D11`, `Platform/Vulkan`) — concrete, working implementations of the above for their respective APIs: DXGI factory/adapter/swapchain and `ID3D11Device` setup for D3D11; full `vk::Instance`/physical-device-selection/queue-family/`vk::Device`/swapchain setup (including required/optional extension lists, ray-tracing extension set, debug report callback) for Vulkan. These are substantially more complete than `RHI::VulkanDevice` (see `docs/rhi.md`), which is a near-empty stub — all of this working logic has *not* been ported over to `RHI/` yet.

- **`Zephyr::IRenderPass`** (`IRenderPass.h`) — pure-virtual-with-defaults interface: `Render(nvrhi::IFramebuffer*)`, `Animate(float)`, `BackBufferResizing/Resized`, `DisplayScaleChanged`, and a full set of GLFW-flavored input callbacks (`KeyboardUpdate`, `MousePosUpdate`, etc.) that return `true` if the event was consumed. Takes a `DeviceManager*` at construction and exposes `GetDevice()`/`GetFrameIndex()` through it. Only usable with the `DeviceManager` stack.

- **`Zephyr::ImGuiRenderPass`** (`RenderPasses/ImGuiRenderPass.h`/`.cpp`) — an `IRenderPass` that owns an `ImGui_NVRHI` struct (vertex/pixel shaders built via `ShaderFactory`, an `nvrhi::InputLayoutHandle`, font texture/sampler, dynamically-grown vertex/index buffers, a per-texture `BindingSetHandle` cache, and PSO). Calls `ImGui::CreateContext()` in its constructor. Also provides font management (`CreateFontFromFile/Memory/MemoryCompressed`, `RegisteredFont`) with DPI-aware rescaling via `DisplayScaleChanged`. This is a self-contained, nvrhi-based (i.e. D3D11/Vulkan-agnostic) ImGui renderer — see "ImGui Integration" below for how it relates to the vendored ImGui backend files.

- **`Zephyr::Renderer`** (`Renderer.h`/`.cpp`) — `final class Renderer : public IModule`. Constructed with `RendererData { GraphicsAPI Api = VULKAN; Ref<Window> Window; }`. `Initialize()` does exactly one thing: `m_DeviceHandle = Device::Create(m_Data.Api);` and returns `true`. Every other lifecycle method (`Shutdown`, `PreUpdate`, `Update`, `PostUpdate`, `PreRender`, `Render`, `PostRenderer`) is an empty override. `GetPriority()` returns `1` and `IsCoreModule()` returns `true`, so `ModuleManager` treats a failed `Renderer::Initialize()` as fatal (`CORE_ASSERT`). `GetDevice()` exposes the owned `Ref<Device>`. This is the class actually registered by `Application::Application()` (`m_ModuleManager.RegisterModule<Renderer>(renderData)` in `Engine/src/Zephyr/Core/Application.cpp`) — i.e. it's the live entry point into rendering, even though it currently renders nothing.

- **`Zephyr::ShaderFactory`** (`ShaderFactory.h`/`.cpp`) — constructed with an `nvrhi::DeviceHandle`, an `Ref<IFileSystem>`, and a base shader path. `CompileShader(fileName, entryName)` drives the Slang compiler (`slang::createGlobalSession`, `ISession`, `IModule`, `IEntryPoint`) to produce DXBC (`sm_5_1`) for D3D11, DXIL (`sm_6_7`) for D3D12, or SPIR-V (`spirv_1_5`) for Vulkan — selected via `m_Device->getGraphicsAPI()` — and writes the result to a `.bin` file next to the source via `IFileSystem`. `CreateShader`/`CreateShaderLibrary` load (compiling on cache miss) and wrap bytecode into `nvrhi::ShaderHandle`/`ShaderLibraryHandle`. `CreateStaticShader`/`CreateStaticPlatformShader` variants accept pre-baked bytecode blobs (`StaticShader { ByteCode, Size }`) instead of going through the filesystem, useful for embedding shaders at compile time. `CreateAutoShader`/`CreateAutoShaderLibrary` try the static path first and fall back to file-based compilation. `FindShaderFromHash(...)` is a declared-but-stub API — it unconditionally returns `{nullptr, 0}`. Only `.slang` files pass `IsShaderExtension`.

## Design Notes

- **The central fact to know about this directory: two device abstractions exist, and only one is live.** `DeviceManager` (+ `D3D11DeviceManager`/`VulkanDeviceManager` + `IRenderPass` + `ImGuiRenderPass`) is a complete, working device/swapchain/render-loop/ImGui stack. `Renderer` (+ `RHI::Device`) is a new, much smaller class that is the one actually constructed by `Application`. A repo-wide search confirms `DeviceManager::Create`, `new D3D11DeviceManager`, `new VulkanDeviceManager`, and `ImGuiRenderPass` are referenced only *within* `Renderer/` itself (declarations/definitions) — nothing in `Editor/` or `Application.cpp` ever instantiates any of them. So today: the engine boots a `Window`, then a `Renderer` module that creates a bare `RHI::Device` and stops there; no swapchain is created, nothing is ever drawn, and ImGui is never initialized in the running app. The old stack is fully functional code sitting dormant, presumably kept around as reference/salvage material while the new `RHI`-based path is built back up to parity. Anyone resuming this work should decide explicitly whether to (a) port the working `VulkanDeviceManager`/`D3D11DeviceManager` logic into `RHI::VulkanDevice`/a new `RHI::Surface` implementation and delete the `DeviceManager` stack, or (b) reconnect `DeviceManager` and delete the new `RHI`/`Renderer` scaffold. Right now both exist, which is exactly the kind of state that causes confusion for anyone new to the branch.

- **`Renderer::Initialize()` doesn't use the `Window` it's given.** `RendererData::Window` is stored in `m_Data` but never passed to `Device::CreateSurface()` — so even the one method that does something doesn't finish the job of standing up a swapchain. This lines up with `RHI::Surface` having no implementation yet (see `docs/rhi.md`).

- **Camera controls are commented out, not missing by omission.** `Camera::NormalCameraControls`/`OrbitCameraControls` have their entire `Input::` polling logic commented out in `Camera::OnUpdate` and within the control functions themselves, along with the `Math::Frustum`/`Math::AABB`-based frustum culling (`IsInsideFrustum`, `m_Frustum`). `FrustumCulling` is still a public bool member with no effect. This looks like it was disabled during the input/math-library churn that's part of this same refactor rather than a finished, input-free camera.

- **`ShaderFactory` is device-stack-agnostic but currently only wireable to `DeviceManager`.** It takes a raw `nvrhi::DeviceHandle`, not a `Zephyr::RHI::Device`, so it doesn't care which stack produced the device — but `RHI::Device` doesn't currently expose an `nvrhi::IDevice*` at all (only `GetGraphicsAPI()`/`CreateSurface()`), so there's no way yet to construct a `ShaderFactory` from the new `Renderer`/`RHI::Device` path without extending `RHI::Device`'s interface first.

- **`FindShaderFromHash` is a stub.** It's declared with a real signature (taking a hash and a `hashGenerator` callback) but the body just returns `{nullptr, 0}` unconditionally — a half-finished feature, not currently functional.

- **D3D12 has no `DeviceManager` implementation either.** `DeviceManager::CreateD3D12()` just returns `nullptr`; there is no `Platform/D3D12/` directory under `Renderer/` (only empty ones under `RHI/`). D3D12 is a named `GraphicsAPI` enum value everywhere but has zero backing implementation in either stack.

### ImGui Integration

`Engine/src/ImGui/` (`imgui_impl_glfw.cpp`/`.h`, `imgui_impl_vulkan.cpp`/`.h`) contains Dear ImGui's own official backend files — not Zephyr code, but copied in (with the project's MIT header prepended) and built as part of the engine. They are functionally identical to the reference copies under `Engine/Vendor/ImGui/backends/`:

- **`imgui_impl_glfw.*`** — the standard GLFW *platform* backend: window/input/clipboard/cursor handling, `ImGui_ImplGlfw_InitForVulkan`/`InitForOpenGL`/`InitForOther`, `NewFrame`, and the GLFW callback installers.
- **`imgui_impl_vulkan.*`** — the standard Vulkan *renderer* backend: a complete `VkPipeline`-based ImGui renderer (`ImGui_ImplVulkan_Init`, texture/descriptor-set management, etc.).

A repo-wide search for `ImGui_ImplGlfw_` / `ImGui_ImplVulkan_` call sites turns up **zero references outside these files and the `Vendor/ImGui` examples** — none of these functions are called anywhere in `Zephyr/` or `Editor/`. Instead, the engine's own `ImGuiRenderPass`/`ImGui_NVRHI` (see above) reimplements ImGui rendering directly against nvrhi, which makes sense as a deliberate choice: the stock `imgui_impl_vulkan.cpp` is Vulkan-only, which would defeat the purpose of an nvrhi-based, API-agnostic renderer. The GLFW platform backend, by contrast, has no such conflict and could in principle still be used for input — but it isn't wired in either, and `DeviceManager::CreateWindowDeviceAndSwapChain()` has its own GLFW callback registration block (key/mouse/scroll/focus/etc.) commented out, so even the "old" stack's path for feeding input into ImGui is currently disconnected. Net effect: both `Engine/src/ImGui/*` and the donut-derived `ImGui_NVRHI` renderer are present in the tree and build, but neither is reachable at runtime today — they're inert alongside the rest of the `DeviceManager` stack, kept presumably for when that stack (or its logic) is reconnected.

## Dependencies

**Renderer depends on:**
- **nvrhi** (`Engine/Vendor/nvrhi`) — `DeviceManager`, `D3D11DeviceManager`, `VulkanDeviceManager`, `IRenderPass`, `ImGuiRenderPass`, and `ShaderFactory` are all written directly against nvrhi types (`nvrhi::IDevice`, `nvrhi::ICommandList`, `nvrhi::ShaderHandle`, `nvrhi::FramebufferHandle`, etc.).
- **GLFW** (`Engine/Vendor/GLFW`) — window creation/polling/DPI queries in `DeviceManager`; also used directly by `Zephyr::Window`.
- **Vulkan SDK** — `vulkan.hpp`/`nvrhi/vulkan.h` for `VulkanDeviceManager`; D3D11/DXGI headers (Windows SDK) for `D3D11DeviceManager`.
- **slang** (`Library["slang"]` in `Dependencies.lua`, resolved from `%{VULKAN_SDK}/Lib/slang.lib` — i.e. Slang ships inside this project's Vulkan SDK install) — `ShaderFactory`'s compiler backend.
- **ImGui** (`Engine/Vendor/ImGui`, plus the copied backend files in `Engine/src/ImGui/`) — `ImGuiRenderPass`.
- `Zephyr::RHI` (`RHI::GraphicsAPI`, `RHI::Device`) — used by the new `Renderer` class.
- `Zephyr::Window`, `Zephyr::Modules::IModule`, `Zephyr::Input`, `Zephyr::FileSystem::IFileSystem` — `Renderer`/`Camera`/`ShaderFactory` depend on these Engine submodules respectively.

**What depends on Renderer:**
- `Zephyr::Application` (`Engine/src/Zephyr/Core/Application.cpp`) registers `Zephyr::Renderer` as a core `IModule` at startup.
- `Editor` (`Editor/src/App.cpp`) includes `Zephyr/Renderer/ShaderFactory.h` (currently an unused/vestigial include — no `ShaderFactory` is constructed there) and otherwise interacts with rendering indirectly through `Zephyr::Application`/ImGui, not through `DeviceManager` or `ImGuiRenderPass` directly.
