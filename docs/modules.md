# Modules

The `Modules` submodule defines Zephyr's plugin/subsystem architecture: a common `IModule` interface that every major engine subsystem (`Window`, `Input`, `Renderer`, and presumably future systems like physics/audio) implements, and a `ModuleManager` that owns, initializes, priority-sorts, ticks, and tears down all registered modules. It exists to give the engine a uniform, decoupled way to compose subsystems and drive their per-frame callbacks, instead of `Application` hardcoding calls into each subsystem by name.

## Key Files

| File | Purpose |
|---|---|
| `IModule.h` | Defines `UpdateFlags` and the `IModule` interface every module implements. |
| `ModuleManager.h` | Declares `ModuleManager`: the registry that owns modules and drives their lifecycle/tick callbacks. |
| `ModuleManager.cpp` | Implements registration bookkeeping, sorting, and the per-phase dispatch loops. |

## Key Types & APIs

- **`UpdateFlags`** (`IModule.h`) — a bitflag `enum class : u32` (`None`, `Update`, `PhysicsUpdate`, `RendererUpdate`, combined via `ENUM_CLASS_FLAG_OPERATORS`) declaring which tick phases a module wants to participate in. A module opts into the update loop, physics loop, and/or render loop independently by returning the appropriate flags (or-ed together) from `GetUpdateFlags()`.

- **`IModule`** (`IModule.h`) — the interface every module implements:
  - Pure virtual: `Initialize()` (returns success/failure), `Shutdown()`, `GetName()`, `GetPriority()`, `GetUpdateFlags()`.
  - `IsCoreModule()` — defaults to `false`; core modules (e.g. `Input` in the current tree) assert on the engine if they fail to initialize (see `ModuleManager::RegisterModule`), whereas a non-core module failing initialization is only logged as an error and the engine continues.
  - Nine empty-by-default per-phase hooks, three per tick stage: `Pre/Update/Post` for `Update`, `PhysicsUpdate`, and `Render` ("`PostRenderer`" is the render-stage's post hook, not `PostRender` — an inconsistent name worth knowing when searching for it). A module only needs to override the hooks relevant to the `UpdateFlags` it declared; the `ModuleManager` gates whether these are even called based on those flags (see below), so overriding a hook without declaring the matching flag is silently inert.

- **`ModuleManager`** (`ModuleManager.h`/`.cpp`) — owns all modules in `std::unordered_map<std::type_index, Ref<IModule>> m_Modules`, keyed by the module's **concrete** C++ type (`typeid(T)`), plus a separately maintained `std::vector<Ref<IModule>> m_UpdateList` used purely for tick ordering.
  - `RegisterModule<T>(Args&&...)` — constructs a `Ref<T>` via `CreateRef<T>(args...)`, stores it in the map under `typeid(T)`, and calls `Initialize()` immediately. On failure it logs an error and asserts if (and only if) `IsCoreModule()` is true, otherwise it lets the (failed) module continue to exist in the registry. Returns the `Ref<T>` so the caller (typically `Application`) can immediately use it (e.g. to hand its GLFW handle to the next module being registered).
  - `GetModule<T>()` — looks up `m_Modules[typeid(T)]` (an `IModule` slot) and `DynCast`s (i.e. `std::dynamic_pointer_cast`) it down to `Ref<T>`. **Must be called with the same concrete type the module was registered under** — this is a type-indexed registry, not an interface registry, so `GetModule<IModule>()` or a base-class lookup won't find anything registered under a derived type.
  - `SortModules()` — rebuilds `m_UpdateList` from the map and sorts by ascending `GetPriority()`. Called once in `ModuleManager::Initialize()`, and again every single frame from `Application::Run()`'s loop (see Design Notes).
  - `PreUpdate/Update/PostUpdate`, `PrePhysics/Physics/PostPhysics`, `PreRender/Render/PostRenderer` — each iterates `m_UpdateList` and calls the matching `IModule` hook only on modules whose `GetUpdateFlags()` includes the corresponding flag (checked via the `Any(value, flag)` helper generated by `ENUM_CLASS_FLAG_OPERATORS`).
  - `Shutdown()` — calls `Shutdown()` on every module, then `reset()`s every `Ref` and clears the map. Also invoked from the destructor, so a `ModuleManager` going out of scope tears down all modules automatically.

- **How modules get registered/ticked in practice.** `Application`'s constructor (`Zephyr/Core/Application.cpp`) is the sole place modules are currently registered: `Window` first, then `Input` (constructed with the window's GLFW handle), then `Renderer` (constructed with a `RendererData` that references the `Window`). `Application::Run()` calls `m_ModuleManager.SortModules()` once per frame, then drives `PreUpdate → Update → PostUpdate → PreRender → Render → PostRenderer` each frame (note: the `PrePhysics/Physics/PostPhysics` triplet is defined on both `ModuleManager` and `Application` but is **not** called anywhere in `Application::Run()` — physics ticking is wired up in the manager/interface but not yet invoked).

## Design Notes

- **Registry is keyed by concrete type, not by interface.** Because `RegisterModule<T>`/`GetModule<T>` both key off `typeid(T)` of the template argument, only one instance of any given concrete module type can ever be registered (a second `RegisterModule<Window>()` call would silently overwrite the first in the map, though `m_UpdateList` would then hold two entries — one stale — until the next `SortModules()` rebuild). There is no way to register multiple instances of the same module type, and no way to look modules up polymorphically by a common base other than `IModule` itself.
- **`GetModule<T>()` has a map `operator[]` side effect.** `m_Modules[typeid(T)]` is a non-const `operator[]`, which inserts a default-constructed (null) `Ref<IModule>` entry into the map if `T` was never registered, rather than just returning `nullptr` without mutating the container. The net observable result (`GetModule<T>()` returning `nullptr`) is correct, but every failed lookup permanently grows the map with an empty slot — a minor but real side effect of using `operator[]` instead of `find()`.
- **`SortModules()` runs every frame.** `Application::Run()` calls `m_ModuleManager.SortModules()` unconditionally each iteration, even though the module set and priorities essentially never change after startup in the current code (nothing dynamically registers/unregisters modules at runtime). This is a full `std::sort` over all modules every frame — cheap at the current module count, but redundant work that would only need to happen on registration/priority changes.
- **Physics phase is unused.** `ModuleManager::PrePhysics/Physics/PostPhysics` and `Application::PrePhysics/Physics/PostPhysics` exist and would correctly gate on `UpdateFlags::PhysicsUpdate`, but `Application::Run()` never calls them. Any module returning `UpdateFlags::PhysicsUpdate` from `GetUpdateFlags()` today would simply never get its `Pre/PhysicsUpdate/Post` hooks invoked — this looks like a half-finished feature (interface + manager plumbing exist, call site doesn't).
- **`UpdateFlags::None` is not the zero value.** `None = BIT(0)` (i.e. `1`), not `0`; `Update`, `PhysicsUpdate`, `RendererUpdate` are `BIT(1)`/`BIT(2)`/`BIT(3)` (`2`/`4`/`8`). Because `None` doesn't share any bits with the real flags, `Any(None, Update)` etc. still correctly evaluates to `false`, so this doesn't currently cause bugs — but it is an unusual choice (`None` is normally `0` in a bitflag enum) and means `None` can't be used as a true "no bits set" identity value if someone later writes code assuming `flags == (EnumType)0` means "nothing set".
- **No explicit dependency ordering between modules beyond registration order + priority.** `Input` is constructed with `Window`'s GLFW handle, so `Window` must be registered first — enforced only by the order of `RegisterModule` calls in `Application`'s constructor, not by any declared dependency mechanism. `GetPriority()` only affects tick order (via `m_UpdateList` sorting), not initialization order (initialization happens synchronously inside `RegisterModule`, in call order). `Window` and `Input` both currently return priority `0`.
- **Threading.** Nothing in `ModuleManager` is synchronized; it assumes single-threaded registration and ticking from `Application::Run()`'s main loop. (`Engine/Vendor/enkiTS/` — a task-scheduling library — is present as an untracked vendor dependency elsewhere in the repo, suggesting multithreading is a planned direction, but `Modules` itself has no thread-safety provisions today.)

## Dependencies

- **Depends on:** `Zephyr/Core/Base.h` (`BIT`, `ENUM_CLASS_FLAG_OPERATORS`, `Ref`/`CreateRef`, `DynCast`, `DISABLE_MOVE_AND_COPY`), `Zephyr/Core/BasicTypes.h` (`u32`, `i32`), `<typeindex>`/`<unordered_map>` from the standard library, and (in `.cpp`) `CORE_INFO`/`CORE_ERROR`/`CORE_ASSERT` logging/assert macros.
- **Depended on by:** `Application` owns a `ModuleManager m_ModuleManager` and drives its lifecycle/tick methods every frame; every current engine subsystem that wants to participate in the frame loop or be discoverable via `Application::Get().GetModule<T>()` implements `IModule` — concretely `Window`, `Input`, and `Renderer` today.
